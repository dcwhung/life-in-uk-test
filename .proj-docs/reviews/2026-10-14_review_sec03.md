## 背景

`api/stats.js` 原本嘅 lockout 只有一個全局 bucket `lifeuk:authfail:<UTC hour>`，每小時 10 次，唔分來源。任何人送 11 個錯嘅 Basic header，owner 就成個鐘登入唔到。

用戶確認嘅方案：
- per-client bucket（每小時 5 次）+ global bucket（每小時 100 次）
- client IP 依次用 `x-real-ip` → `x-forwarded-for` 第一個 → `unknown`
- IPv6 歸一到 /64
- client id = HMAC(key = sha256(`STATS_PASSWORD`), ip|hour) 取 16 hex，唔存 raw IP，TTL 1 小時
- 先 INCR 再驗密碼，保留 W-384 嘅並發保護

### 🟡 W-389：被鎖 client 嘅 429 仍然會先佔 global slot
- **位置**：`api/stats.js` `isLockedOut`
- **問題**：同一個 IP 並發 flood 期間，in-flight request 佔住 global slot。實測 300 個並發 request，owner 喺另一個 IP 用正確密碼都收到 **429**。而且每個被鎖 request 要用 6 個 Redis command（300 個 request 共 1,796 個），令 SEC-02 嘅配額問題放大 3 倍。
- **方案**：
  - A：先查 per-client，未超先碰 global（**採用**）
  - B：Lua `EVAL`
  - C：維持現狀，只改 comment

### 🟡 W-391：HMAC key 由密碼衍生
- **問題**：任何讀到 Redis 嘅人，都可以用 key 離線驗證密碼。
- **方案**：
  - A：用獨立 env secret
  - B：用 scrypt 之類嘅慢 KDF
  - C：維持設計，寫明密碼要求
- **用戶決定（2026-10-14）：方案 C**。`STATS_PASSWORD` 必須 ≥ 20 個隨機字元，唔可以喺其他地方重用。

### 🟢 S-293（可選）
- **位置**：`normalizeIp`
- **問題**：IPv6 尾段嵌住 dotted IPv4 時，IPv4 實際佔 2 個 group 但只當 1 個計，令 `/64` 計錯。例如 `1::3:4:5:6:1.2.3.4` 得出 `1:0:0:3`，應該係 `1:0:3:4`。Vercel 唔會送呢種寫法。
- **處理**：✅ `b8f2395` fix: S-293 normalizeIp counts an embedded IPv4 tail as two groups（TDD 紅 → 綠；`telemetry-api-test` 93 asserts PASS）。

### 已接受嘅殘餘風險
- **分散式攻擊**：攻擊者用多個 IP（每個都未過 5 次）並發攻擊，仍然可以暫時超出 global 上限；用約 20 個 /64 就可以鎖住 owner 一個鐘。用戶已經接受。
- **共用出口 IP**：同一個 CGNAT 出口 IP（或者 `unknown` fallback）背後嘅攻擊者，可以鎖住 owner 嘅 per-client bucket。
- **IP header 假設**：Vercel 會覆寫 `x-real-ip` / `x-forwarded-for`，係根據 Vercel 文件嘅假設。如果 header 可以偽造，per-client 限制會失效，但仍然有 global 100 兜底。
